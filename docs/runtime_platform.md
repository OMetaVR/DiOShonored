# Platform layer (Phase 2): user32/gdi32, d3d9, dsound, XInput, DirectInput over SDL3 and DXVK-native

Everything here lives in `runtime/platform/` and is built into the same runtime object library as the rest of `runtime/` (see `docs/runtime.md` for the core).
SDL3 is a hard dependency of the runtime now (`pkg-config sdl3`); DXVK-native is `dlopen`ed at run time and only its headers are needed at build time.

## Process and thread model

- The guest runs on its own pthread (`thread_run_main`); the **process main thread owns SDL** (window creation, event polling, display queries, `SDL_Vulkan` surface creation on iOS). Guest-side HLE reaches it with `mainthread_call(fn)` (blocking) / `mainthread_post(fn)`; `dishonored_linux` pumps the queue and `SDL_PollEvent` in its main loop and forwards events with `platform_route_event`. When no host loop is running (unit tests, tools) `mainthread_call` runs inline and `PeekMessage`/`GetMessage`/`XInputGetState` pump SDL themselves.
- SDL video/audio/gamepad subsystems are initialised lazily (`platform_video_init`, first `CreateWindowEx`/`DirectSound*`/`XInput*` call), so a headless run that never opens a window never touches them.
- Guest-visible state that is queried at very high rates is mirrored in atomics and never calls into SDL: key state (`GetKeyState` 4.8 M calls in the trace), focus/foreground window (`GetFocus` 182 k), cursor position (`GetCursorPos`, `GetCursorInfo` 45 k), clip rect, window rects (`ScreenToClient` 45 k, `GetWindowThreadProcessId` 45 k).

## user32 (`win32_user32.cpp`, `win32_input.cpp`, `win32_keys.cpp`)

- **Classes and windows.** `RegisterClass[Ex]A/W`, `CreateWindowEx[A/W]` build a window record (style, ex style, class, wndproc, extra bytes, user data, title, rect). Top-level windows get an SDL window (hidden, Vulkan-capable, borderless unless `WS_CAPTION`, resizable with `WS_THICKFRAME`); child windows are records only. `AdjustWindowRect` and the client/outer conversion use one frame model (Windows 7 Aero numbers: an overlapped window is 8/31/8/8 px larger than its client area), so a game that asks for a 1280x720 client gets exactly that. Creation sends `WM_NCCREATE`, `WM_NCCALCSIZE`, `WM_CREATE`, and for `WS_VISIBLE` the `ShowWindow` sequence (`WM_SHOWWINDOW`, `WM_SIZE`, `WM_MOVE`, `WM_ACTIVATEAPP`, `WM_ACTIVATE`, `WM_SETFOCUS`) by calling the guest WndProc through `guest_invoke_from(esp, ...)`.
- **Message queue.** One queue per guest thread. `PeekMessage` has a lock-free empty fast path (63 k calls in the trace); `GetMessage` blocks with a short timed wait; `PostMessage/PostThreadMessage/PostQuitMessage`, `SendMessage[Timeout]` (direct call of the WndProc), `DispatchMessage` (WndProc or `SetTimer` callback), `CallWindowProc`, `DefWindowProc` (`WM_CLOSE` -> `DestroyWindow`, Alt+F4, `SC_CLOSE`, activation, text), `WaitMessage`, `RegisterWindowMessage`, `SetTimer/KillTimer` (timer messages are generated on demand when a queue is polled).
- **SDL -> WM_\* translation** (main thread): close request -> `WM_CLOSE`; resize/move/minimise/maximise -> `WM_SIZE`/`WM_MOVE`; focus gained/lost -> `WM_ACTIVATE`, `WM_SETFOCUS/KILLFOCUS`, `WM_ACTIVATEAPP` and key state reset; key down/up -> `WM_KEYDOWN/UP` (or `WM_SYS*` with Alt) with Windows virtual keys and PS/2 set-1 scan codes, the extended-key, repeat and transition bits; SDL text input -> `WM_CHAR` (plus the control characters Enter/Backspace/Tab/Esc); mouse motion/buttons/double clicks/X buttons/wheel -> `WM_MOUSEMOVE`, `WM_*BUTTON*`, `WM_MOUSEWHEEL` with MK_* flags. `TranslateMessage` is a no-op because characters arrive as text-input events.
- **Cursor and input state.** `ShowCursor` counter -> `SDL_ShowCursor/HideCursor`; `ClipCursor/GetClipCursor` -> window mouse rect + grab; `SetCursorPos` -> warp; `GetCursorInfo`, `SetCursor/GetCursor/LoadCursor/LoadIcon/LoadImage` (handles only), `SetCapture/ReleaseCapture`, `GetKeyState/GetAsyncKeyState/GetKeyboardState`, `MapVirtualKey*`, keyboard layout calls (fixed en-US), `SendInput` (accepted, ignored), hooks and hot keys (accepted, never invoked), device notifications.
- **Display.** `GetSystemMetrics`, `SystemParametersInfoA/W`, `EnumDisplaySettings[Ex]A/W` (current + the SDL fullscreen mode list), `EnumDisplayDevicesA/W`, `EnumDisplayMonitors`, `GetMonitorInfoA/W`, `MonitorFrom*`, `ChangeDisplaySettings*` (reports success; D3D9 performs the real mode switch), `MessageBoxA/W` (logged, returns `IDOK`), `DialogBoxParamW` (logged, returns -1), clipboard (empty), `GetDC/ReleaseDC/BeginPaint/EndPaint`.
- Unimplemented user32 functions (the rest of the 95 in the import list are covered) are auto-stubs.

## gdi32 (`gdi32.cpp`)

Memory DCs, DIB sections and compatible bitmaps live in guest memory; `SelectObject`, `GetObjectW`, `GetDeviceCaps` (real desktop size, 96 dpi), `GetPixel/SetPixel`, `StretchBlt` (nearest), `GetDIBits`, stock objects, `CreateFontIndirectW`, colours and modes. **There is no glyph rasteriser**: `TextOutW` draws nothing and `GetTextExtentPoint32W` returns a plausible fixed-pitch size.

## d3d9 -> DXVK-native (`d3d9_*.cpp`, generated `d3d9_generated.inc`)

- **Objects.** A guest D3D9 object is the 16-byte COM object of `core/com.cpp` (`vtbl`, `host id`, `refcount`, `cookie`). One shared guest vtable exists per interface (15 interfaces: IDirect3D9, Device9, SwapChain9, Surface9, Volume9, Texture9, CubeTexture9, VolumeTexture9, VertexBuffer9, IndexBuffer9, VertexDeclaration9, VertexShader9, PixelShader9, StateBlock9, Query9); each slot is a normal thunk-table entry whose `GuestFn` is the method, so lifted code calls `guest_call(vtbl[slot])` and the thunk reads `this` and its stack arguments, calls the DXVK C++ method, pops the right number of bytes. Reference counts are kept on the guest object; the guest object owns exactly one host reference. A host pointer maps to one guest object for its whole life (identity map: `GetBackBuffer` twice, `GetRenderTarget` after `SetRenderTarget` return the same guest pointer, `GetContainer` / `QueryInterface` reuse the wrapper), and `Release` to zero drops the host reference. This is exact enough that DXVK's own "device reset needs all D3DPOOL_DEFAULT resources released" check passes and fails correctly (`test_d3d9` covers both).
- **Generated thunks.** `runtime/tools/gen_d3d9.py` parses `d3d9.h` (the DXVK copy of the MinGW header) and emits **226 generated + 28 hand-written thunks, 0 unsupported**, in vtable order. Argument kinds: 32-bit values and enums, floats, `HWND` (guest handle -> `SDL_Window*`), `REFIID`, guest COM pointers in (-> host object), out interface pointers (-> new or existing wrapper written back to the guest), layout-identical structs passed through by pointer (D3DCAPS9, D3DVIEWPORT9, D3DSURFACE_DESC, D3DLIGHT9, D3DMATERIAL9, D3DVERTEXELEMENT9, RECT, matrices, ... — `static_assert`ed against the 32-bit Windows sizes), `HANDLE*` shared handles (always NULL). Every host call is wrapped in `try/catch` and maps escapes to `D3DERR_DRIVERINTERNALERROR`.
- **Hand-written** (`d3d9_manual.cpp`): `CreateDevice`, `Reset`, `CreateAdditionalSwapChain`, `GetPresentParameters` (32-bit `D3DPRESENT_PARAMETERS` <-> host struct with a pointer-sized `HWND`; `CreateDevice`/`Reset` run on the main thread so the Vulkan surface is created there), `GetCreationParameters`, `GetAdapterIdentifier` (the host struct is 4 bytes longer), `GetAdapterMonitor`, and all of Lock/Unlock. `Surface::GetDC/ReleaseDC` are loud stubs (`D3DERR_NOTAVAILABLE`, logged, counted).
- **Lock/Unlock.** Host memory cannot be aliased into the 4 GiB window, so every lock gets a guest-memory staging buffer from a size-class pool (power-of-two, up to 16 cached per class, backed by the guest heap): the host lock happens at `Lock` time, the data is copied host -> guest unless `D3DLOCK_DISCARD`, and copied back guest -> host at `Unlock` unless `D3DLOCK_READONLY` (sub-rect and block-compressed extents are computed per format so the copy never reads past the host allocation). Handled for buffers, 2-D textures, cube faces, surfaces, volume textures and volumes (the 12-byte guest `D3DLOCKED_BOX` / 8-byte `D3DLOCKED_RECT`). Measured: a 64 KiB `DISCARD` lock + fill + unlock cycle is about 7.5 us (about 8.5 GB/s of staged traffic).
- **Backends.** DXVK-native is one `D3d9Backend` behind a registry (`DISH_D3D9_BACKEND` selects); iOS will get a direct Metal backend behind the same seam: `docs/runtime_d3d9_backend.md`. `Device::Present` and `SwapChain::Present` are hand-written so the app-lifecycle safe point (`lifecycle_park`) runs after every present.
- **DXVK loading.** `Direct3DCreate9` loads `libdxvk_d3d9.so.0` (`DISH_DXVK_LIB`, the loader path, then the in-repo `third_party/dxvk/install-linux`; on Apple `@executable_path/Frameworks/libdxvk_d3d9.0.dylib`), sets `DXVK_WSI_DRIVER=SDL3`, `DXVK_LOG_LEVEL=warn` and keeps the pipeline cache under `<save-dir>/DXVK`.
- **Hot-call cost** (`test_d3d9 hot_call_overhead`, minimum of 7 runs, NVIDIA RTX 3060 Ti, DXVK 3.1.1, direct C++ call vs `guest_call` through the guest vtable):

| method | direct | via thunk | overhead |
|---|---|---|---|
| SetPixelShaderConstantF (1 vec) | 7.5 ns | 10.5 ns | +3 ns |
| SetVertexShaderConstantF (4 vec) | 8.8 ns | 12.2 ns | +3.4 ns |
| SetRenderState | 5.4 ns | 8.9 ns | +3.5 ns |
| SetSamplerState | 5.4 ns | 9.8 ns | +4.4 ns |
| SetTexture | 4.6 ns | 10.5 ns | +5.9 ns |
| DrawIndexedPrimitive (tiny quad) | 45-61 ns | 56-64 ns | +3-12 ns |

  The path is allocation-free and lock-free: thunk-table index, `com_host_object_raw` (cookie compare + table load), argument decode, one virtual call. The 14 M `SetPixelShaderConstantF` per 5 minutes of the trace cost about 0.5 ms of CPU per second at this rate.
- **Acceptance test.** `test_d3d9` re-expresses the `tools/spikes/d3d9_test` scene (DXT1/DXT5 textures with mips, render-to-texture, 2-stream vertex declaration, SM3.0 shaders, alpha blend, D24S8) as a fake guest client that only calls through guest vtables, renders it, reads the back buffer through `GetRenderTargetData` + a guest `LockRect`, and compares with the spike's direct renderer on the same GPU: **0 of 230,400 pixels differ**. Set `DISH_KEEP_SHOTS=<dir>` to keep both images as PPM. A second test runs the guest on its own thread with the process main thread pumping SDL (the iOS shape) and gets the identical image.

## dsound (`dsound.cpp`)

`DirectSoundCreate/8` (also reached through `CoCreateInstance(CLSID_DirectSound8 {3901CC3F-...})`, which is how the trace shows Wwise creating it), `DirectSoundEnumerateA/W`, `GetDeviceID`, capture entry points failing with `DSERR_NODRIVER`. `IDirectSound(8)`: `CreateSoundBuffer`, `GetCaps`, `DuplicateSoundBuffer`, `SetCooperativeLevel`, `GetSpeakerConfig` (stereo), `Initialize`. `IDirectSoundBuffer(8)`: `Lock/Unlock` (two regions on wrap, `ENTIREBUFFER`, `FROMWRITECURSOR`), `GetCurrentPosition`, `Play` (looping), `Stop`, `SetCurrentPosition`, `GetStatus`, `SetVolume/Pan/Frequency`, `GetFormat`, `GetCaps`, `QueryInterface` between the buffer interfaces; the primary buffer accepts `SetFormat`/`Play`. Secondary buffers live in guest memory, so `Lock` returns a direct pointer and `Unlock` is free. An `SDL_AudioStream` callback (or a silent real-time clock thread when no device exists) mixes every playing buffer to 48 kHz stereo float: 8/16/24/32-bit PCM and float, any channel count and sample rate (linear resampling, `SetFrequency`), volume in 1/100 dB and pan, clipping at 1.0; the play cursor tracks the mixed position and the write cursor is 40 ms ahead. Measured: a 16 KiB looping ring followed the way the trace shows (`GetCurrentPosition` polling, `Lock/Unlock` refills) wraps at the expected rate and mixes 101% of real time. Not implemented: `IDirectSoundNotify`, 3D buffers, effects (`SetFX` fails), hardware buffers.

## XInput 1.3 (`xinput.cpp`)

`XInputGetState` (and the undocumented `GetStateEx`, ordinal 100), `XInputSetState` (SDL rumble, left/right motors), `XInputGetCapabilities`, `XInputGetBatteryInformation`, `XInputEnable`, `XInputGetKeystroke`; imported by name or by ordinal 2/3 as the game does. Up to four SDL gamepads (opened on hot-plug events, `GameController.framework` on iOS) map to user indices 0..3 in connection order. `XINPUT_GAMEPAD` packing: buttons `0x0001..0x8000` (A=0x1000 from SDL "south"), triggers 0..255, thumbs raw `int16` with Y inverted to XInput's up-positive, **no dead zone**, packet number increments on any change. Test: a virtual SDL gamepad stands in for the Backbone, including hot-plug and ordinal binding.

## DirectInput 8 (`dinput8.cpp`)

`DirectInput8Create` (IDirectInput8 A/W), `EnumDevices`, `CreateDevice` for `GUID_SysMouse` and `GUID_SysKeyboard`. Mouse: `SetDataFormat` (DIMOUSESTATE/2), `SetProperty(DIPROP_BUFFERSIZE)`, `SetCooperativeLevel` (exclusive -> SDL relative mouse mode), `Acquire/Unacquire`, buffered `GetDeviceData` (X/Y/Z/button events from the SDL stream, `DIGDD_PEEK`) and immediate `GetDeviceState`. Keyboard: 256-byte DIK state from the key table. Force feedback, action maps and game controllers return `DIERR_UNSUPPORTED` (pads come in through XInput).

## Tests

`ctest` has 19 executables; the platform ones are `test_window` (class/window/message flow, key and mouse translation, timers, posting, display and cursor APIs, close/destroy/quit), `test_d3d9` (5 tests, see above), `test_dsound`, `test_input`. They need a display and a Vulkan device; without one they exit with code 77 and ctest reports them as skipped. They call SDL directly to inject events (`SDL_PushEvent`), so the translation code is exercised exactly as for real input.

## iOS notes and Linux-only items

- Nothing in the hot paths depends on Linux: the Win32 query fast paths are atomics, the d3d9 path is vtable calls into DXVK, the dsound mixer only uses `SDL_AudioStream`. All `platform/*.cpp` files (including the d3d9 ones against the DXVK headers and the 32-bit layout `static_assert`s) syntax-check for `arm64-apple-ios15.0`.
- Must stay on the main thread on iOS: window creation/destruction, `SDL_PollEvent`, display queries, Vulkan surface creation (`CreateDevice` and `Reset` are routed through `mainthread_call`; a swapchain recreated implicitly inside `Present` after a resize still runs on the guest thread — to be revisited on the device). `SDL_Vulkan` window creation uses the `SDL_PROP_WINDOW_CREATE_VULKAN_BOOLEAN` property; MoltenVK/`DXVK_VULKAN_LIBRARY` selection is documented in `research/platform/graphics_path.md`.
- Ported for iOS (see `docs/runtime_ios.md`): the fault handler (Mach exception ports). Still Linux-only / needs porting: `/tmp` fallback for anonymous file mappings, the default `DISH_DXVK_LIB` search path, `libdxvk_d3d9.so.0` naming (the Apple names are in the loader list but untested), and `SDL_AUDIODRIVER=dummy` used by the tests.

## Known gaps

- No glyph rendering in gdi32; `DialogBoxParamW`, clipboard, `Surface::GetDC`, `IDirectSoundNotify`, DirectSound 3D/effects, DirectInput force feedback/action maps are unsupported.
- `TranslateMessage` is a no-op (characters come from SDL text input), so IME composition and dead keys are as SDL delivers them; the keyboard layout is fixed en-US.
- Window positions on Wayland are not known to the application (SDL reports 0,0), so screen coordinates are window-relative there.
- Fullscreen exclusive/mode switches rely on DXVK-native's SDL3 WSI; `ChangeDisplaySettings*` only reports success. Multi-monitor: one monitor is reported.
- `SendInput` is ignored; hooks are accepted but never called.
- d3d9: `D3DPOOL_DEFAULT` vs `MANAGED` is whatever DXVK does; `GetFrontBufferData`, `SetGammaRamp`, `SetCursorProperties` are forwarded and may be no-ops in DXVK; shared handles are always NULL; `IDirect3D9Ex`/`Device9Ex` are not exposed.
