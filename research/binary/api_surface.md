# Spike 0.1 / 0.2: host API surface of `Dishonored.exe` and the DLLs we would recompile

Measured (not inferred) unless marked *inferred*. Static data: PE import/delay-import/export tables parsed with `pefile`
(`tools/analysis/imports.py`). Runtime data: Proton trace of about 8 minutes of startup (`tools/analysis/trace_proton.sh`, see
"Runtime trace" below and `tools/analysis/trace_proton.md`). Machine-readable lists: `tools/analysis/out/api_surface.json` and
`api_surface.tsv` (one row per imported function with importer modules and trace evidence), `imports_per_module.json` (all modules, all imports and exports),
`os_api_surface_static.txt`, `api_called_startup_r480.txt` (Win32 calls seen), `api_called_not_in_static_imports.txt`.
The full import lists are also in `private/api/` (regenerated by the scripts).

## 1. Summary

- **Scenario A, CRT recompiled with the rest** (exe + binkw32 + PhysX x5 + APEX x8 + `msvcr90` + `msvcp90`): the HLE runtime must provide
  **420 unique Win32/COM-entry functions across 14 host DLLs**: kernel32 234, user32 95, wsock32 26, gdi32 20, advapi32 13, winmm 12, ole32 6,
  d3d9 4, shell32 3, oleaut32 2, xinput1_3 2, dinput8 1, iphlpapi 1, powrprof 1.
- **Scenario B, CRT replaced by a native implementation** (recommended for speed, see `lifter_decision.md`): **366** OS functions
  (kernel32 drops from 234 to 180; the other DLLs are unchanged) plus the CRT export surface actually imported:
  **231 `msvcr90`/`msvcr80` functions** (msvcr90 227 = exe's 145 plus the APEX DLLs' and `msvcp90`'s; msvcr80 38 from the Vorbis DLLs; union 231; all msvcr80 names exist in msvcr90) and **9 `msvcp90` functions** (all
  `std::basic_ostream<wchar_t>`/`_Mutex`/`uncaught_exception`/`wcerr` pieces).
- The exe alone needs 278 of the 420 (kernel32 129, user32 82, wsock32 25, gdi32 12, advapi32 9, ole32 6, winmm 2, d3d9 4, shell32 3, oleaut32 2, xinput 2, dinput8 1, powrprof 1).
- Seen in the startup trace: 153 of the 420 OS functions plus 71+18 CRT functions (counts below). The rest are not proven unused, only unseen.
- COM entry points are a much larger surface than the import lists suggest. Observed d3d9 (about 90 distinct interface methods), DirectSound (about 20), DirectInput8 (about 10) and
  XInput (2) usage is in section 5.
- **Not needed by the exe at all (no import, no string, not loaded in the trace):** the Ogg/Vorbis DLLs (`ogg`, `vorbis`, `vorbisfile`, `vorbisenc`; they import `msvcr80`, which is not in the install),
  `wxmsw28*` (editor), `cudart*`/`nvcuda` (PhysX GPU; need only a "no CUDA device" stub because `PhysXCore` links `cudart32_30_9` statically), `SteamAPIUpdater`, `msvcm90`.
  The 8 APEX DLLs and `NxCharacter`/`PhysXExtensions` were also not loaded during startup (only `PhysXLoader`, `PhysXCooking`, `PhysXCore` were).

## 3. Imports of the exe from DLLs that are stubbed or special

- **steam_api.dll** (18, stub): `SteamAPI_Init`, `SteamAPI_Shutdown`, `SteamAPI_RunCallbacks`, `SteamAPI_RegisterCallback`, `SteamAPI_UnregisterCallback`,
  `SteamAPI_RegisterCallResult`, `SteamAPI_UnregisterCallResult`, `SteamApps`, `SteamFriends`, `SteamGameServer`, `SteamGameServer_Shutdown`, `SteamMatchmaking`,
  `SteamMatchmakingServers`, `SteamNetworking`, `SteamRemoteStorage`, `SteamUser`, `SteamUserStats`, `SteamUtils`.
  The accessors return C++ interface pointers; a stub must return guest-memory objects with vtables (guest 32-bit pointers) whose methods return benign values.
- **libcurl.dll** (7, stub): `curl_global_init`, `curl_global_cleanup`, `curl_easy_init`, `curl_easy_setopt`, `curl_easy_perform`, `curl_easy_cleanup`, `curl_slist_append`.
  In the trace libcurl was active (about 59 `select`, 17 `send`, 12 `recv`, 8 `socket`, 4 `connect`): the game does HTTP at startup. The stub should fail `curl_easy_perform` fast.
- **dbghelp.dll** (12, stub): `SymInitialize`, `SymSetOptions`, `SymGetOptions`, `SymSetSearchPath`, `SymLoadModule64`, `SymGetModuleBase64`, `SymGetModuleInfo64`, `SymFunctionTableAccess64`,
  `SymGetSymFromAddr64`, `SymGetLineFromAddr64`, `StackWalk64`, `MiniDumpWriteDump` (crash reporting).
- **faultrep.dll** (1): `ReportFault`. **powrprof.dll** (1): `CallNtPowerInformation`.
- **binkw32.dll** (20 imports by the exe, recompile or skip movies): `_BinkOpen@8`, `_BinkClose@4`, `_BinkDoFrame@4`, `_BinkNextFrame@4`, `_BinkWait@4`, `_BinkPause@8`, `_BinkGoto@12`, `_BinkGetRects@8`,
  `_BinkGetError@0`, `_BinkGetKeyFrame@12`, `_BinkGetRealtime@12`, `_BinkShouldSkip@4`, `_BinkRegisterFrameBuffers@8`, `_BinkGetFrameBuffersInfo@8`, `_BinkSetIOSize@4`, `_BinkSetSoundSystem@8`,
  `_BinkOpenDirectSound@4`, `_BinkSetSoundTrack@8`, `_BinkSetVolume@12`, `_BinkSetPan@12`.
  binkw32 delay-loads `mss32.dll` (19 functions, Miles Sound System; not shipped). Observed at runtime: binkw32 itself calls `LoadLibraryA("DSOUND.DLL")` then `DirectSoundCreate`.
- **PhysXLoader.dll** is delay-imported by the exe (6): `NxCreatePhysicsSDK`, `NxReleasePhysicsSDK`, `NxGetPhysicsSDK`, `NxGetPhysicsSDKAllocator`, `NxGetCookingLib`, `NxGetUtilLib`.

- **Exports of the exe**: 216, nearly all `AK::` (Wwise SoundEngine/MemoryMgr/StreamMgr/MusicEngine) symbols, for Wwise plugins.

## 5. Runtime trace (Proton, startup only)

How: `tools/analysis/trace_proton.sh relay|com <seconds>` (game launched through Steam so that `steam_api` works; Proton - Experimental, Wine 11; `WINEDEBUG=+relay` filtered to calls whose caller is
a game module via `RelayFromInclude`; COM via Wine's `+d3d9,+dsound,+dinput,+xinput,+ole` with wined3d instead of DXVK). Relay only sees calls into Wine *builtin* DLLs, and COM methods only via the second mode.

Coverage actually reached: process start, `Software\Arkane\Dishonored` registry init, window creation, D3D9 device creation, PhysX init, a long run of UPK/TFC file opens that ends at the UI/font packages (`UI_Gamma_SF.upk`,
`DisFonts_SF.upk`, `Lighting.tfc`), about 7,800 `Present` calls (movies/loading), and a continuous input/message loop. The game was **killed at 480 s (relay) and 300 s (com); whether it reached the main menu is not confirmed**
(no screenshot was taken on purpose; the game's own log is not written in the shipping build). Gameplay-level coverage needs a human to play (`trace_proton.sh relay 0`).

Totals for the relay run: 283 unique functions called from game modules (28 million calls): kernel32 94, msvcr90 76, user32 43, ws2_32 30, ntdll 10 (kernel32 forwards), advapi32 7, combase 4, winmm 3, lsteamclient 3, xinput1_3 2,
oleaut32 2, and one each of wsock32, shell32, shcore, secur32, powrprof, ole32, dsound, dinput8, ddraw.

## 6. Method notes and limits
- Static lists are complete for imports and delay-imports. Calls made through `GetProcAddress` are only the ones observed (section 4).
- `msvcr80` is imported by the Ogg/Vorbis DLLs only; the install ships only `msvcr90`/`msvcp90`/`msvcm90`. If those DLLs were ever needed, alias `msvcr80` to `msvcr90` (all 38 imported names exist in `msvcr90`).
- Wine forwards some kernel32 functions to ntdll, so the trace shows `ntdll.Rtl*` names (`RtlAllocateHeap` = `HeapAlloc`, `RtlInitializeCriticalSection`, ...); `tools/analysis/merge_api.py` maps these back.
- `RelayExclude` hides ultra-hot functions (`TlsGetValue`, critical sections, `Interlocked*`, `GetLastError`, `HeapAlloc/Free`, `QueryPerformanceCounter`, `GetTickCount`, `memcpy`...). They are in the import table, so they are assumed used.
- The trace is one startup session under Wine; behaviours that differ on Windows (e.g. GPU vendor probing paths) can add calls.
